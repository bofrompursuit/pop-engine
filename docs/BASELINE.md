Setup steps live in `DEPLOY.md`. Provider SDKs (`pg`, `@aws-sdk/client-s3`, `resend`, `twilio`, `node-pg-migrate`) install with their consuming issue, not the scaffold.

**Artifact checksums:** the current ruleset row above carries a `sha256` digest, per `ARCHITECTURE-FUTURE.md` §14 step 5, which requires a published artifact to carry version, checksum, changelog and approval metadata before this manifest is updated. The digest is **SHA-256 over the exact bytes of the file at the path in that row**, with nothing normalised, no key reordering and no whitespace stripped, so it is reproducible with one command and depends on nothing but the file:

```
sha256sum rules/nyc-rules.v2.8.json
```

It lives here rather than inside the artifact because a digest stored in the file it covers would change the bytes it describes. `pnpm check:baseline` recomputes it and fails on a mismatch, so a ruleset edited without republishing, or a row left pointing at a digest that no longer matches, breaks the build rather than going unnoticed. Stating the algorithm and the coverage is the point: a checksum whose derivation is not written down cannot be verified by anyone later.

**Superseded artifacts:** a published ruleset is never deleted, but through Phase 1.5 it is retained in **git history** rather than as a second file under `rules/`, which holds exactly one artifact at a time. Each lineage row above names the commit, so recovery is one command and needs nothing that is not in the repository:

```
git show 0122eca:rules/nyc-rules.v2.6.json > /tmp/v26.json
# sha256 40ffed1e7b42cf94e9eaa26172ac2024bd5748f02600320e286c79037962a073
git show e4f04b1:rules/nyc-rules.v2.7.json > /tmp/v27.json
# sha256 f5a06df604e100f95ccb9b1457c12969419c0f6c720e8702b380634c7c8b3c3e
```

A recovered artifact parses and evaluates like any other, because the engine takes a ruleset document rather than a path. That is what makes AD-7 replay work: `permit_plans` pins `ruleset_version` and stores `intake_snapshot`, and the artifact for that version comes from its lineage commit. `packages/engine/src/__fixtures__/nyc-rules.v2.3.json` is a copy taken for exactly that purpose by the replay test on #97. Digests for superseded versions are recorded here for verifying a recovery; `check:baseline` does not recompute them, because the file is deliberately not on disk.

`ARCHITECTURE-FUTURE.md` §§5 and 14 describe per-version artifact paths and a `rules/fixtures/<ruleset_version>` layout. That document is the Phase 2+ target and says so in its own status header, which states it is not the build instruction for Phase 0–1.5; neither layout exists yet. So the two are not in conflict: this records the mechanism in force now, and §14 records the one Phase 2+ moves to.

**Version conventions (current):** ruleset `nyc.vMAJOR.MINOR` · rules schema `popengine-rules/v2` · fixtures follow the ruleset version they derive from. Full semver-per-artifact (per `docs/proposals/baseline-manifest-codex-draft.md`) is a Phase 2 upgrade.
